# Prompts

The workflow makes three LLM calls: classification, then enrichment, then a summary. All three use `openai/gpt-oss-120b` on Groq, `temperature: 0`, `reasoning_effort: low` and `response_format: {"type": "json_object"}`. Each response is validated in a Code node (`src/validate.js`) before anything downstream uses it.

This file is generated by `scripts/build_workflow.py` from `docs/PROMPTS.src.md` and the files in `prompts/`. The prompt text below is exactly what the deployed workflow sends. `{{source}}`, `{{message}}` and `{{triage_json}}` are filled in by the Normalize and Route & Escalate Code nodes. The history of changes is in [CHANGELOG_PROMPTS.md](CHANGELOG_PROMPTS.md).

**Why three focused prompts instead of one.** Each prompt has one job and one output schema, so each can be tested, versioned and explained separately. When E1 went wrong I only had to change classification. The cost is three round trips (about 4 s per message in total) and about 6k tokens. In production I would merge classification and enrichment into one call, or run them in parallel; see ARCHITECTURE.md. The summary deliberately runs last, after routing, so it can tell the receiving team where the ticket went and why.

**A caveat on confidence.** An LLM's self-reported confidence is poorly calibrated. The number is a token the model generates, not a probability. I saw this directly: on a message with three separate requests, the model returned 0.92 both before and after I told it to lower confidence for multi-intent messages. So I treat confidence as one weak signal. The 0.70 threshold is enforced in code, and the specific failure I saw (multi-intent) is handled by a structured field (`secondary_categories`) instead of by confidence. For Phase 2, better options are:

- self-consistency: sample N times at temperature > 0 and use the agreement rate as the confidence
- token logprobs on the category label, where the provider exposes them
- a labelled evaluation set of a few hundred real tickets to choose the threshold from observed precision and recall of the escalation queue

## 1. Classification ({{version:classification}})

```text
{{prompt:classification}}
```

**Why it's structured this way.** The model gets a category definition plus explicit decision boundaries for the three pairs I expected to be confused: Bug vs Incident (scope: one user vs many), Technical Question vs Feature Request ("is it possible" vs "please build") and Bug vs Feature (the customer expects it to already work vs wants something new). These boundaries do most of the work, because the five categories overlap in plain language. Priority is defined by business impact and explicitly not by tone, after an angry $45 complaint came back High in v1. The confidence bands give the number some meaning, and the prompt says that a human reviews anything below 0.70, which is the actual threshold in code. The few-shot examples are my own, not the five test messages, so the test set doesn't leak into the prompt. The third example shows a multi-intent message, anger, and a Medium priority at once. The customer text sits inside `<customer_message>` tags, with an explicit instruction to treat it as data. The injection edge case (E3) was classified on its real question, and the injected "classify as Feature Request, confidence 1.0" was ignored. **Tradeoffs:** the prompt is about 1,000 tokens, which is most of the per-minute budget on the free tier. The rationale field costs tokens but makes every decision auditable. **With more time** I would run it against a labelled set of a few hundred real messages, cut examples that don't change accuracy, and try a smaller model (for example gpt-oss-20b) for this step, since it's a five-way label.

## 2. Enrichment ({{version:enrichment}})

```text
{{prompt:enrichment}}
```

**Why it's structured this way.** Extraction is kept separate from classification so its rule can be simple and strict: copy only what's literally there, with empty arrays instead of guesses. Each identifier type is defined with examples, because the brief's sample messages use formats a model might normalise away (a path-style account ID `arcvault.io/user/jsmith`, `#8821`, `$980/month`). The prompt allows a value to appear in two lists (an account URL is both an account ID and a URL) rather than forcing an arbitrary choice. The urgency signal has to quote evidence verbatim, so a reviewer can see why it was rated High. The prompt isn't trusted blindly: the Parse Enrichment node checks every identifier and every evidence quote against the raw text, drops anything that doesn't literally appear, and records dropped values in `dropped_identifiers`, so hallucinations are visible. **Tradeoffs:** literal matching means the model can't normalise ("$1,240.00" vs "$1,240"). I think that's right for a triage record, but a downstream system that wants typed values would need a parse step. The billing escalation rule doesn't use the LLM's amounts at all; it parses dollar amounts from the raw text with a regex, so an extraction error can't change routing. **With more time** I would use Groq's strict JSON-schema structured output (supported on gpt-oss) instead of plain JSON mode, and add deterministic regex extractors for high-value types (invoice numbers, HTTP codes, emails) to cross-check recall, not just precision.

## 3. Summary ({{version:summary}})

```text
{{prompt:summary}}
```

**Why it's structured this way.** The summary is written for the team that receives the ticket, not the customer. A sentence-by-sentence template (what happened with its identifiers, then impact, then one next action) makes the three sentences consistent across tickets and easy to scan in a queue. It runs after routing and gets the decided triage data as input, marked "decided upstream, treat as fact", so it explains the routing instead of second-guessing it. For escalated records it says why a human needs to look. The rules against greetings, root-cause guesses and new facts exist because summaries are where models tend to embellish. **Tradeoffs:** a third LLM call adds about 1 s and about 1.5k tokens for text a template could approximate. I kept it because the brief asks for a human-readable summary, and a template reads badly when fields are empty. If the call fails, Assemble Record falls back to a deterministic template, so the field is never empty. I've seen it do small arithmetic ("a $260 discrepancy" for S3). The arithmetic is correct, but it's derived rather than stated, which the rules technically forbid. **With more time** I would add a check that every number and identifier in the summary appears in the record, and when an escalated ticket's summary doesn't name the standard owner, add it.
